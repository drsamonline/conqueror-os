# Localisation

Conqueror OS speaks **English, Hindi and Gujarati** in its shell — the sidebar, the
navigation, the search box and every ARIA label — and, since 3.5.0, on the **Today
screen**: the landing page a reader actually sees. This document is how that works and
what is still English.

## The shape of it

Three things, in this order:

| | What | Where |
|---|---|---|
| 1 | The **English** | `src/index.html` — `data-i18n`, `data-i18n-attr`, the nav table, and `t("key","English")` call sites |
| 2 | The **translations** | `src/locales/en.json`, `hi.json`, `gu.json` |
| 3 | The **runtime catalogue** | the `<script id="i18n-data" type="application/json">` block in `src/index.html` |

`tools/extract-strings.py` is the only thing that moves data between them:

```
python3 tools/extract-strings.py --print   # what it reads out of the source
python3 tools/extract-strings.py --write   # regenerate en.json + the inline block
python3 tools/extract-strings.py --check   # exit 1 on any drift (this is the CI step)
```

The direction matters. The English is read **out of the source**, never out of a
catalogue, so a catalogue can be regenerated but cannot become the truth. That is what
makes drift impossible instead of merely unlikely.

## Why the English stays in the markup

The alternative — keys everywhere and a catalogue that holds the English too — means
every screen reads a key and every reader has to look up what it says. The app is a
single file people open from disk; the strings should be legible where they are used.
So `<h3 data-i18n="shell.recent">Recent</h3>` is both the English and the declaration,
and the tool reconciles it with the catalogues.

## Adding a language

1. Copy `src/locales/en.json` to `src/locales/<code>.json` and translate the values.
2. Add `<code>` to `LANGS` in `tools/extract-strings.py`.
3. Add the language's own name to `I18N_LANG_NAMES` in `src/index.html`
   (`{ en:"English", hi:"हिन्दी", gu:"ગુજરાતી" }`) — a language is named in its own
   language, because a reader looking for Gujarati is not looking for the word
   "Gujarati" in whatever the interface is currently set to.
4. `python3 tools/extract-strings.py --write && npm test`.

## Adding a string

Write it in English in one of the three declaring places, then run `--write`. The
tool will fail loudly if a key is declared twice with different text, if a value is
empty, or if an attribute-declaring element does not actually carry that attribute.

## What the checks refuse

`--check` fails on: a key in the markup with no catalogue entry; a catalogue key
nothing declares; a language missing a key; an **untranslated** value (one identical to
the English — the failure mode where a language ships and changes nothing); an empty
value; and an inline block that is stale, reformatted or hand-edited. The block is
compared as text, not as parsed JSON: a parsed comparison accepts a duplicate key,
because the last one wins and the two dictionaries then look identical.

`tests/i18n.test.js` is the runtime half — 63 assertions that boot the real app and
check that switching language changes the navigation, the sidebar, the search hint,
the placeholder, the breadcrumb and the ARIA labels; that `<html lang>` follows; that
the choice is written to storage and survives a reload; that an unknown language is
refused without losing the current one; and that a key missing from Hindi falls back
to English, then to the caller's own literal, then to the key.

Since 3.5.0 it also drives the **Today view**: that its title, lede, widget headings,
section titles, empty states and day counter are English on open and Hindi after
`set("hi")`, with the hash unchanged (the view re-renders in place rather than waiting
for a navigation); that a translated line keeps its markup (`<kbd>` survives); that no
English leaks into the rendered Hindi view; and that switching to Gujarati and back to
English restores each in turn.

The orphan check no longer keeps a hand-list of call-site keys: it scans
`t("key","English")` out of the same script the app runs, so localising a view cannot
make its own keys look orphaned.

## Localising a view

No new tool is needed. The extraction pass already reads `t("key","English")` call
sites; what a view needed was to *use* them. Three steps, in this order:

1. Wrap the English in the template literal: `'<h3>'+t("view.today.mission.title",
   "Today's Mission")+'</h3>'`. Keep the English beside the key — it is still the
   source, and it is still readable where it is used.
2. `python3 tools/extract-strings.py --write` — en.json and the inline block pick the
   new keys up; `hi.json` and `gu.json` gain them with the English copied in, which
   `--check` then refuses until step 3.
3. Translate the new keys in `hi.json` and `gu.json`, then `--check` and `npm test`.

Two rules that are not obvious:

- **Do not escape a translated line that is meant to be markup.** The shortcut line
  carries `<kbd>` elements, so it is inserted as HTML; the catalogue is ours, and the
  suite asserts the `<kbd>` survives. Anything a reader supplies is escaped as before.
- **`render()` replaces `#main`'s children.** A test that captures an element before
  switching language is reading a detached node — re-query instead. (This bit the 3.5.0
  suite on its first run.)

## What is still English

Six views: the Reader, the Journal, Trackers, Challenges, Insights and Settings — plus
modals, toasts, and the export and print surfaces. **Today is done** (3.5.0, 47 keys):
title, lede, streak ribbon, the three widgets, the active-challenge card and its empty
state, the reading-goal bar, the resume banner, the four section titles, both empty
states and the shortcut line. **The Library is done** (3.6.0, 14 keys): the heading,
the lede, both section titles and their calls to action, the per-book counts (with a
singular), the chapter time cell, the empty chapter list, and the per-chapter status
word. The shell was done first because it is the part every screen shares; Today second
because it is the screen every session opens on; the Library third because it is where
Today sends you.

**Authored content is not in the catalogue and should not be.** Book titles,
descriptions, chapter titles, part headings and chapter bodies are the book's own text;
translating them is an authoring job with a content licence attached, not a key added to
`hi.json`.

Right-to-left support is **not** implemented: Hindi and Gujarati are both LTR, so
there is nothing yet to mirror. `document.documentElement.lang` is set, which is what
a future RTL language would key off.
